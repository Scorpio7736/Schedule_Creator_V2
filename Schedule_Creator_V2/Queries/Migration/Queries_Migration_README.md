# Migration Queries

This folder contains the SQL used to initialize the Schedule Creator V2 LocalDB database on first run.

Despite the folder name `Migration`, the current implementation is primarily a **database bootstrap system** rather than a versioned migration framework. These scripts create the initial database, schema, and tables when the application determines that its LocalDB database file does not yet exist.

The scripts are used by:

```text
Services/
└── Database/
    └── DataMigragtion.cs
```

> **Note:** `DataMigragtion.cs` is the current class/file name in the project. The spelling is preserved here so the documentation matches the code.

---

## Folder Overview

| File | Query Resource | Purpose |
| --- | --- | --- |
| `CreateDatabase.sql` | `Queries.CreateDatabase` | Creates the `Schedule_Creator_V2` LocalDB database and its MDF/LDF files. |
| `CreateSchemas.sql` | `Queries.CreateSchemas` | Creates the `[UWGB]` database schema. |
| `CreateTables.sql` | `Queries.CreateTables` | Creates the application's initial database tables. |

The overall initialization flow is:

```text
Application starts
        |
        v
DataMigragtion.EnsureDatabaseExists()
        |
        v
Does AppData.mdf exist?
      /     \
    yes      no
     |        |
     |        v
     |   CreateDatabaseFile()
     |        |
     |        v
     |   CreateDatabase.sql
     |        |
     |        v
     |   CreateDatabaseSchema()
     |        |
     |        +--> CreateSchemas.sql
     |        |
     |        +--> CreateTables.sql
     |        |
     |        v
     |   Display welcome message
     |
     v
Application continues
```

# How Migration Queries Are Loaded

The SQL files are registered in `Queries.resx`.

That allows application code to access them through generated properties such as:

```csharp
Queries.CreateDatabase
Queries.CreateSchemas
Queries.CreateTables
```

The migration service therefore does not need to manually locate or read the `.sql` files at runtime.

The normal relationship is:

```text
Migration SQL file
      |
      v
Queries.resx
      |
      v
Generated Queries property
      |
      v
DataMigragtion.cs
      |
      v
SQL Server LocalDB
```

# `CreateDatabase.sql`

## Purpose

Creates the physical SQL Server LocalDB database used by Schedule Creator V2.

## Current SQL

```sql
CREATE DATABASE
    Schedule_Creator_V2
ON
    (
        NAME = Schedule_Creator_V2,
        FILENAME = '{databaseFileName}'
    )
LOG ON
    (
        NAME = Schedule_Creator_V2_Log,
        FILENAME = '{logFileName}'
    )
```

This script contains two placeholders:

```text
{databaseFileName}
{logFileName}
```

These are **not SQL parameters**.

Instead, `DataMigragtion.CreateDatabaseFile()` replaces the placeholders in the SQL string before executing it.

Conceptually:

```csharp
var createDbSql = Queries.CreateDatabase
    .Replace(
        "{databaseFileName}",
        databaseFileName)
    .Replace(
        "{logFileName}",
        logFileName);
```

The resulting SQL contains the actual file-system paths where SQL Server should create the database files.

---

## Database Name

The SQL database is named:

```text
Schedule_Creator_V2
```

This matches the `Initial Catalog` used by the application's primary LocalDB connection string.

---

## MDF File

The primary database file is:

```text
AppData.mdf
```

`DataMigragtion.GetDatabaseFileName()` builds its path under the current Windows user's Local Application Data directory.

The resulting location is conceptually:

```text
%LOCALAPPDATA%
└── Schedule_Creator_V2
    └── AppData.mdf
```

For example:

```text
C:\Users\<User>\
    AppData\
    Local\
    Schedule_Creator_V2\
    AppData.mdf
```

The actual user profile path is determined at runtime.

---

## LDF File

The SQL Server transaction-log file is generated by replacing:

```text
.mdf
```

with:

```text
_log.ldf
```

Therefore:

```text
AppData.mdf
```

becomes:

```text
AppData_log.ldf
```

The final folder is expected to contain:

```text
Schedule_Creator_V2/
├── AppData.mdf
└── AppData_log.ldf
```

---

# Why Database Creation Uses a Different Connection

Normally, the application's database services connect using:

```text
LocalDbConnection
```

which specifies:

```text
Initial Catalog=Schedule_Creator_V2
```

That connection cannot be used to create the database when the database does not yet exist.

For that reason, database creation uses:

```text
LocalDbConnectionMaster
```

which connects to:

```text
Initial Catalog=master
```

The sequence is:

```text
LocalDbConnectionMaster
        |
        v
SQL Server master database
        |
        v
CREATE DATABASE Schedule_Creator_V2
        |
        v
Application database now exists
        |
        v
LocalDbConnection can be used
```

This is why `CreateDatabaseFile()` creates its own `SqlConnection` instead of using the normal `Database.ExecuteNonQuery()` helper.

# `CreateSchemas.sql`

## Purpose

Creates the schema used to organize Schedule Creator V2's application tables.

## Current SQL

```sql
CREATE SCHEMA [UWGB] AUTHORIZATION dbo
```

The application's tables are therefore referenced using names such as:

```text
[UWGB].[Staff]
[UWGB].[Availability]
[UWGB].[DaysOff]
[UWGB].[JobSettings]
[UWGB].[Schedule]
```

rather than being created directly under:

```text
dbo
```

---

## Schema Ownership

The script specifies:

```sql
AUTHORIZATION dbo
```

which means the schema is owned by the database's `dbo` principal.

---

## Called By

After the database file has been created, `DataMigragtion.CreateDatabaseSchema()` executes:

```csharp
ExecuteNonQuery(
    Queries.CreateSchemas);
```

This must happen **before** `CreateTables.sql`, because the table script creates tables inside `[UWGB]`.

The required order is therefore:

```text
Create database
      |
      v
Create [UWGB] schema
      |
      v
Create [UWGB] tables
```

## Purpose

Creates the application's initial database tables.

UWGB.Staff
UWGB.Schedule

# `UWGB.Availability`

## Definition

```sql
CREATE TABLE [UWGB].[Availability] (
    [id]           INT      NOT NULL,
    [dayOfTheWeek] INT      NOT NULL,
    [startTime]    TIME (2) NOT NULL,
    [endTime]      TIME (2) NOT NULL
);
```

## Purpose

Stores recurring weekly availability ranges for staff members.

## Columns

| Column | Type | Nullable | Purpose |
| --- | --- | --- | --- |
| `id` | `INT` | No | Staff member ID. |
| `dayOfTheWeek` | `INT` | No | Day of week represented numerically. |
| `startTime` | `TIME(2)` | No | Start of availability. |
| `endTime` | `TIME(2)` | No | End of availability. |

A staff member can have multiple availability rows.

Conceptually:

```text
Staff ID 4
   |
   +--> Monday      2:45 PM - 8:15 PM
   +--> Tuesday     2:45 PM - 6:15 PM
   +--> Wednesday   5:30 PM - 8:15 PM
```

---

# `UWGB.DaysOff`

## Definition

```sql
CREATE TABLE [UWGB].[DaysOff] (
    [id]     INT           NOT NULL,
    [Date]   DATE          NOT NULL,
    [reason] NVARCHAR (50) NOT NULL
);
```

## Purpose

Stores specific calendar dates on which a staff member is unavailable.

This differs from `Availability`, which describes recurring weekly availability.

## Columns

| Column | Type | Nullable | Purpose |
| --- | --- | --- | --- |
| `id` | `INT` | No | Staff member ID. |
| `Date` | `DATE` | No | Date the staff member is unavailable. |
| `reason` | `NVARCHAR(50)` | No | Reason for the day off. |

Conceptually:

```text
Availability
    = recurring weekly schedule

DaysOff
    = specific calendar exceptions
```

---

# `UWGB.JobSettings`

## Definition

```sql
CREATE TABLE [UWGB].[JobSettings] (
    [DayOfWeek]   NVARCHAR (50) NOT NULL PRIMARY KEY,
    [OpeningTime] TIME (2)      NOT NULL,
    [ClosingTime] TIME (2)      NOT NULL
);
```

## Purpose

Defines the operating hours for each day that the schedule can use.

## Columns

| Column | Type | Nullable | Purpose |
| --- | --- | --- | --- |
| `DayOfWeek` | `NVARCHAR(50)` | No | Name of the operating day. |
| `OpeningTime` | `TIME(2)` | No | Opening/start time. |
| `ClosingTime` | `TIME(2)` | No | Closing/end time. |

## Primary Key

`DayOfWeek` is the table's primary key.

Therefore:

```text
Monday
```

can have only one `JobSettings` row at a time.

This matches the application's current assumption that one opening/closing range exists for each configured day.

---

# `UWGB.Staff`

## Definition

```sql
CREATE TABLE [UWGB].[Staff] (
    [id]          INT           IDENTITY (1, 1) NOT NULL,
    [fName]       NVARCHAR (50) NOT NULL,
    [mName]       NVARCHAR (50) NULL,
    [lName]       NVARCHAR (50) NOT NULL,
    [position]    NVARCHAR (50) NOT NULL,
    [email]       NVARCHAR (50) NOT NULL,
    [belayCert]   NVARCHAR (50) NOT NULL,
    [certifiedOn] DATE          NULL,
    [expiresOn]   DATE          NULL,
    PRIMARY KEY CLUSTERED ([id] ASC)
);
```

## Purpose

Stores the primary record for each staff member.

## Columns

| Column | Type | Nullable | Purpose |
| --- | --- | --- | --- |
| `id` | `INT IDENTITY` | No | Auto-generated staff ID. |
| `fName` | `NVARCHAR(50)` | No | First name. |
| `mName` | `NVARCHAR(50)` | Yes | Middle name. |
| `lName` | `NVARCHAR(50)` | No | Last name. |
| `position` | `NVARCHAR(50)` | No | Staff role/position. |
| `email` | `NVARCHAR(50)` | No | Email address. |
| `belayCert` | `NVARCHAR(50)` | No | Belay-certification state stored as text. |
| `certifiedOn` | `DATE` | Yes | Certification date. |
| `expiresOn` | `DATE` | Yes | Certification expiration date. |

---

## Identity Logic

The staff ID uses:

```sql
IDENTITY (1, 1)
```

so SQL Server automatically creates IDs:

```text
1
2
3
4
...
```

`CreateStaff.sql` therefore does not supply an `id` value.

---

## Primary Key

The table defines:

```sql
PRIMARY KEY CLUSTERED ([id] ASC)
```

making the generated staff ID the unique primary identifier for staff records.

---

# `UWGB.Schedule`

## Definition

```sql
CREATE TABLE [UWGB].[Schedule]
(
    [dayOfWeek]    NVARCHAR(50) NOT NULL,
    [staffID]      INT          NULL,
    [scheduleName] NVARCHAR(50) NOT NULL,
    [startTime]    TIME(2)      NOT NULL,
    [endTime]      TIME(2)      NOT NULL,
);
```

## Purpose

Stores individual shift rows belonging to saved schedules.

## Columns

| Column | Type | Nullable | Purpose |
| --- | --- | --- | --- |
| `dayOfWeek` | `NVARCHAR(50)` | No | Day on which the shift occurs. |
| `staffID` | `INT` | Yes | Assigned staff ID. May be `NULL`. |
| `scheduleName` | `NVARCHAR(50)` | No | Name grouping rows into one saved schedule. |
| `startTime` | `TIME(2)` | No | Shift start. |
| `endTime` | `TIME(2)` | No | Shift end. |

---

## Schedule Grouping

The current schema does not have a separate table such as:

```text
ScheduleHeader
```

with a unique schedule ID.

Instead, schedule rows are grouped by the text value:

```text
scheduleName
```

Conceptually:

```text
Fall 26 - Final Draft
        |
        +--> Monday / Staff 1 / 2:45 - 8:15
        +--> Monday / Staff 2 / 2:45 - 6:15
        +--> Monday / Staff 3 / 4:45 - 8:15
        |
        +--> Tuesday / Staff 1 / ...
```

Each assignment is its own database row.

---

## Nullable `staffID`

The column:

```sql
[staffID] INT NULL
```

allows an unassigned shift to exist.

In C#, `DatabaseCreate.CreateSchedule` converts a missing staff ID into:

```csharp
DBNull.Value
```

before executing the insert.

---

# Current Table Relationships

The application logically relates several tables through staff IDs:

```text
UWGB.Staff.id
      |
      +------> UWGB.Availability.id
      |
      +------> UWGB.DaysOff.id
      |
      +------> UWGB.Schedule.staffID
```

However, the current `CreateTables.sql` does **not** create SQL Server foreign-key constraints for these relationships.

Therefore SQL Server itself does not currently enforce:

- that an Availability ID exists in Staff
- that a DaysOff ID exists in Staff
- that a Schedule `staffID` exists in Staff
- cascade-delete behavior
- referential cleanup

Those relationships are currently managed by application logic.

---

# Current Keys and Constraints

The initial schema is intentionally lightweight.

## Defined Keys

The current script defines:

```text
UWGB.Staff.id
    -> primary key

UWGB.JobSettings.DayOfWeek
    -> primary key
```

## Tables Without Primary Keys

The current script does not define primary keys for:

```text
UWGB.Availability
UWGB.DaysOff
UWGB.Schedule
```

That means duplicate rows are technically possible unless the application prevents them.

For example, SQL Server itself would not currently prevent two identical availability rows such as:

```text
id = 4
day = Monday
start = 14:45
end = 20:15
```

from being inserted twice.

# Data-Type Conventions

The migration schema determines how application types are stored.

| Application Concept | SQL Type | Example |
| --- | --- | --- |
| Staff ID | `INT` | `4` |
| Staff role | `NVARCHAR(50)` | `Shift_Lead` |
| Job-settings day | `NVARCHAR(50)` | `Monday` |
| Availability day | `INT` | Numeric `DayOfWeek` value |
| Schedule day | `NVARCHAR(50)` | `Monday` |
| Time | `TIME(2)` | `14:45:00` |
| Calendar date | `DATE` | `2026-08-25` |
| Belay certification | `NVARCHAR(50)` | `True` / `False` |

One important current detail is that days of the week are not stored consistently across all tables:

```text
Availability.dayOfTheWeek
    -> INT

JobSettings.DayOfWeek
    -> NVARCHAR

Schedule.dayOfWeek
    -> NVARCHAR
```

Application services handle the required enum/string conversions.

# First-Run Initialization Logic

`DataMigragtion.EnsureDatabaseExists()` checks whether the MDF file exists.

Conceptually:

```csharp
var databaseExists =
    DatabaseExists();

if (databaseExists)
{
    return;
}

CreateDatabase();
```

`DatabaseExists()`:

1. Calculates the expected MDF path.
2. Determines the containing directory.
3. Creates the directory if necessary.
4. Checks whether the MDF file exists.

If it exists:

```text
No migration SQL is executed.
```

If it does not:

```text
CreateDatabase.sql
      |
CreateSchemas.sql
      |
CreateTables.sql
```

are executed.

---

# Important: This Is Not Yet Versioned Migration

The current system answers one question:

```text
"Does AppData.mdf exist?"
```

It does **not** currently determine:

```text
"What schema version is this database?"
```

That distinction matters.

For example, suppose version 1 of the application creates:

```text
UWGB.Staff
```

and a future version adds:

```text
phoneNumber
```

to the Staff table.

Changing only `CreateTables.sql` would correctly create the new column for **new users**, but existing users would still have the old database because:

```text
AppData.mdf already exists
        |
        v
EnsureDatabaseExists()
        |
        v
returns without running CreateTables.sql
```

Therefore, modifying these bootstrap scripts alone does not migrate existing installations.

---

# Future Versioned Migration Pattern

If Schedule Creator V2 eventually needs database upgrades across releases, a migration-version system could be introduced.

For example:

```text
DatabaseVersion
      |
      v
Current version = 2
Required version = 4
      |
      +--> Run Migration_2_to_3.sql
      |
      +--> Run Migration_3_to_4.sql
      |
      v
Update DatabaseVersion = 4
```

Possible migration scripts could include:

```text
Migration_001_InitialSchema.sql
Migration_002_AddStaffPhone.sql
Migration_003_AddScheduleId.sql
Migration_004_AddForeignKeys.sql
```

This would allow schema changes such as:

```sql
ALTER TABLE
    [UWGB].[Staff]
ADD
    [phoneNumber] NVARCHAR(25) NULL;
```

to be applied to existing databases safely.

The current project does not implement this system yet; this section describes the architectural distinction for future maintenance.

# Adding a New Table for Fresh Installations

If a new table is needed for newly created databases, it can currently be added to:

```text
CreateTables.sql
```

For example:

```sql
CREATE TABLE [UWGB].[Example]
(
    [id] INT IDENTITY(1,1) NOT NULL,
    [name] NVARCHAR(100) NOT NULL,

    PRIMARY KEY ([id])
);
```

Then create the corresponding application pieces:

```text
Models/
    -> record/model

Queries/Create/
    -> INSERT query

Queries/Read/
    -> SELECT query

Queries/Update/
    -> UPDATE query if needed

Queries/Delete/
    -> DELETE query if needed

Services/Database/
    -> CRUD service methods
```

Remember that changing `CreateTables.sql` affects only databases created after that change unless a versioned migration is also introduced.

---

# Adding a New Schema

If another SQL schema is required, add it to:

```text
CreateSchemas.sql
```

before any table creation that depends on it.

For example:

```sql
CREATE SCHEMA [Reporting]
AUTHORIZATION dbo;
```

The order must remain:

```text
CREATE SCHEMA
      |
      v
CREATE TABLE [Reporting].[...]
```

A table cannot be created inside a schema that does not yet exist.

# Resource Registration

All three current migration scripts are registered in `Queries.resx`:

```text
Queries.CreateDatabase
Queries.CreateSchemas
Queries.CreateTables
```

When adding another SQL resource that should be called through the generated `Queries` class, register the file in `Queries.resx` as well.

Keeping the `.sql` file in the folder without registering or explicitly loading it does not automatically make it part of the application startup process.

# Initialization Responsibilities

The migration system intentionally separates several responsibilities.

## `CreateDatabase.sql`

Responsible for:

```text
physical database creation
MDF location
LDF location
database name
```

## `CreateSchemas.sql`

Responsible for:

```text
logical SQL schema creation
```

## `CreateTables.sql`

Responsible for:

```text
initial table structure
columns
data types
primary keys
nullability
```

## `DataMigragtion.cs`

Responsible for:

```text
deciding whether initialization is needed
calculating file paths
replacing database-file placeholders
selecting the master connection
executing the migration scripts in order
displaying the first-run welcome message
```

Keeping these responsibilities separated makes the initialization process easier to inspect and maintain.

---

# Current Initialization Sequence

The exact high-level sequence is:

```text
1. Application starts

2. EnsureDatabaseExists()

3. Calculate:
   %LOCALAPPDATA%\Schedule_Creator_V2\AppData.mdf

4. Create containing directory if missing

5. Check whether AppData.mdf exists

6. If it exists:
       initialization stops

7. If it does not exist:
       connect to LocalDB master

8. Execute CreateDatabase.sql
       -> create MDF
       -> create LDF

9. Switch back to normal application database connection

10. Execute CreateSchemas.sql
       -> create [UWGB]

11. Execute CreateTables.sql
       -> Availability
       -> DaysOff
       -> JobSettings
       -> Staff
       -> Schedule

12. Display welcome message

13. Continue application startup
```

# Current Maintenance Notes

The following points reflect the current implementation and are useful when modifying the migration system:

- The migration folder currently performs **initial database creation**, not incremental/versioned migration.
- Existing databases are detected solely by checking whether `AppData.mdf` exists.
- If the MDF exists, `CreateSchemas.sql` and `CreateTables.sql` are not run.
- Updating `CreateTables.sql` therefore does not automatically update databases already installed on users' machines.
- Database creation requires `LocalDbConnectionMaster` because the application database does not yet exist.
- `{databaseFileName}` and `{logFileName}` are replaced in C# before `CreateDatabase.sql` is executed.
- The database files are stored beneath `%LOCALAPPDATA%\Schedule_Creator_V2`.
- The `[UWGB]` schema must be created before the table script runs.
- `UWGB.Staff` and `UWGB.JobSettings` currently define primary keys.
- `UWGB.Availability`, `UWGB.DaysOff`, and `UWGB.Schedule` currently do not define primary keys.
- The schema currently does not define foreign-key constraints between staff and related records.
- Day-of-week storage currently varies by table: Availability uses `INT`, while JobSettings and Schedule use `NVARCHAR`.
- `belayCert` is currently stored as `NVARCHAR(50)` rather than SQL `BIT`.
- Schedule rows are grouped by `scheduleName`; there is no separate schedule-header table or schedule ID.
- `Schedule.staffID` is nullable so unassigned shifts can be stored.
- Any future schema changes intended for existing users will require more than editing `CreateTables.sql`; a versioned migration mechanism or equivalent upgrade process will be necessary.

Update this README whenever the first-run initialization flow, database location, schema, table definitions, or migration strategy changes.
